# USER passkeys: policy and threat model

Passkeys are optional on the **USER portal** (`https://portal.biel.dev.br`). The ADMIN Hub supports separate passkeys **only for recovery of the normal ADMIN login password** when both `VIRKI_PASSKEYS_ENABLED=true` and `VIRKI_ADMIN_PASSKEYS_ENABLED=true`. These credentials never authorize ADMIN passwordless login or administrative elevation. Cloudflare Access and the separate administrative credential remain authoritative. The ADMIN flag defaults to off. Disabling it stops new hub ceremonies and ADMIN recovery completion immediately without deleting credentials.

## Ceremonies

The USER production RP ID/origin are exactly `portal.biel.dev.br` / `https://portal.biel.dev.br`; ADMIN recovery uses a **distinct** RP ID/origin `hub.biel.dev.br` / `https://hub.biel.dev.br`. Existing passkeys are migrated to RP `portal.biel.dev.br` and cannot be used in ADMIN recovery, including after a role change. Wildcard subdomains and cross-RP reuse are rejected. Development-only `http://localhost:3001` requires non-production `NODE_ENV` and `VIRKI_PASSKEYS_LOCAL_TESTING=true`.

ADMIN enrollment requires a current authenticated ADMIN session on the hub, a valid Cloudflare Access authorization, session-bound CSRF proof, current **normal** password, a fresh TOTP code if configured, and an independently verified `ADMIN_CREDENTIAL_CHANGE` elevation activated within ten minutes. The same role, active session, current factor policy, active elevation, RP ID and challenge are checked when the signed registration is committed. An ADMIN may rename or revoke a hub passkey only under the same current proofs. The separate administrative password is never replaced or used as a WebAuthn login shortcut. ADMIN recovery accepts passkeys only when an active hub RP credential was previously enrolled and its signed UV assertion passes the one-time challenge, per-credential revision CAS, account role and RP checks. The usual combinations with email/TOTP or another active administrator remain required. Loss of Cloudflare Access cannot be recovered through this flow; it must be restored through its external administrative process.

- **Registration**: an active USER portal session, session-bound CSRF token, current password and (when TOTP is active) a fresh TOTP code. A challenge lasts five minutes, is tied to the USER, session, host, ceremony type and random HTTP-only browser nonce. Its stored digest binds both the current password verifier and the second-factor policy and credential state after the TOTP proof. The server rechecks this binding under the account/session locks before the credential is created and after the audit write; starting, confirming, revoking or replacing a TOTP factor invalidates pending enrollment even when the account remains logged in. Normal consumption of a TOTP step alone does not change the binding. `userVerification: required` and `residentKey: preferred` support both discoverable and older non-discoverable security keys. Registration never replaces a password, TOTP or recovery mechanism.
- **Discoverable login**: no email is supplied; the browser selects an enrolled credential. Only after validating the authenticator's signature does the server use the stored, globally unique credential ID to determine the USER. The optional `userHandle` must match the same USER ID. The claimed account or role in request JSON is never trusted. Every assertion requires user presence and user verification.
- **Non-discoverable login**: specifying an email requires the current password first, with source/account rate limits. Only this proof authorizes disclosure of that user's `allowCredentials` IDs/transports. WebAuthn then authenticates the credential; this yields a session marked `pwd` + `webauthn`, with **no** synthetic `mfa`.
- **Management**: the security page lists, names, and revokes credentials. Each write requires session-bound CSRF, fresh password and current TOTP if configured. Account and live session locks serialize mutations with logout and account deactivation. A session authenticated by passkey alone cannot enroll/revoke credentials without knowing the password.

The server stores only credential ID, COSE public key, counter, backup eligibility/state, transports, optional display name, timestamps and revocation. It never stores fingerprint/PIN/face data, private keys or raw challenge material. Challenges are stored as SHA-256 digests and are consumed by a single guarded database update, including before failed signature verification. An expired or already-consumed challenge cannot create another session. Bounded cleanup removes expired challenge rows. Signature verification uses `@simplewebauthn/server` and exact origin/RP ID. Authentication requires the signed BE (backup-eligible) bit to match the credential's original registration; BE is immutable for that credential, while signed BS (current backup state) can switch only for an eligible credential. The underlying verifier validates the *individual* assertion's BE/BS combination but does not compare BE to historical registration without this explicit check. Authentication uses a counter compare-and-swap and separate revision CAS, including when synced authenticators report counter zero. A zero counter is not evidence of tampering; nor does a nonzero counter prove cloning impossible.

Only verified assertions create an active USER session, and a successful commit includes minimized security audit events. Passkey-only sessions set `authenticationMethods: ["webauthn"]` and OIDC `amr: ["webauthn"]`, `acr: "urn:virki:loa:1"`. Password + passkey records both methods but still never self-promotes to `mfa` or `loa:2`. OIDC freshness, grant checks and project boundaries remain enforced separately.

## Adversaries, limits, recovery

Phishing origins, wrong RP hashes, missing UV, substituted public keys, switched user handles, replay, concurrent assertions, revoked credentials and changed account state must all be rejected. WebAuthn verifies possession of a credential; it cannot guarantee that a synced passkey resides only on physical device hardware or that the sync provider is trusted. A compromised logged-in browser may start a ceremony but cannot enroll or revoke without password (plus configured TOTP). The server does not grant stronger ADMIN assurance based on a passkey.

Loss of all passkeys does not disable password login or existing email/TOTP and recovery procedures. Recovery never discloses or reconstructs private passkey keys; after authenticating through the established recovery flow, a USER can revoke lost credentials and enroll new ones. Disabling the rollout flag is the immediate operational rollback; removing credential tables would irreversibly discard enrolled passkeys and is not a normal rollback.

Local checks: `npm run test:passkeys`; `node scripts/passkeys-disposable-postgres.mjs` (isolated PostgreSQL 18, including a connection in the `America/Porto_Velho` timezone and physical lock/expiry races); and, in Windows PowerShell, `$env:VIRKI_E2E_PASSKEYS='true'; npm run test:e2e -- passkeys.spec.mts` (isolated Linux Docker, TLS `portal.localhost`, Chromium CDP virtual authenticator). The browser scenario covers registration, discoverable login (`["webauthn"]`), account-selected password-assisted login (`["pwd", "webauthn"]`), inventory, revocation and rejected login after revocation. The local test RP is opt-in and never accepted in production.

Before enabling in production, obtain independent security review and manual coverage of platform authenticators and physical security keys. Real cloud devices, sync-provider behavior and accessibility across mobile browsers still require release-specific verification. A signed *synthetic software-key* regression can prove that BE0→BE1 and BE1→BE0 assertions are rejected, BE1/BS0↔BE1/BS1 and counter-zero sessions are accepted, and two distinct counter-zero assertions serialize under PostgreSQL revision CAS; it **cannot** prove Windows Hello, a FIDO2 USB/NFC key, a mobile authenticator, a sync provider or a real cross-device passkey. Record each of those physical acceptance runs separately (device/browser/OS/version, discoverable and account-selected flows, user verification, BE/BS, rollback/revocation, OIDC amr/acr), with no user secrets or raw attestation payloads in a PR.
