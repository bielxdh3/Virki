# USER passkeys: policy and threat model

Passkeys are optional on the **USER portal** (`https://portal.biel.dev.br`). The ADMIN Hub is excluded even when the rollout flag is enabled: ADMIN credentials, Cloudflare Access and the existing elevation workflow remain authoritative. Rollout defaults to disabled; set `VIRKI_PASSKEYS_ENABLED=true` only after migrations and the security review. Reverting the flag disables registration, login and management immediately without deleting credentials. The stored rows remain available if the rollout resumes.

## Ceremonies

The production relying-party ID is exactly `portal.biel.dev.br`, and the permitted WebAuthn origin is exactly `https://portal.biel.dev.br`. Neither `hub.biel.dev.br` nor wildcard subdomains are accepted. Development-only `http://localhost:3001` requires **both** non-production `NODE_ENV` and `VIRKI_PASSKEYS_LOCAL_TESTING=true`; that setting must never be used to authorize a production origin.

- **Registration**: an active USER portal session, session-bound CSRF token, current password and (when TOTP is active) a fresh TOTP code. A challenge lasts five minutes, is tied to the USER, session, host, ceremony type and random HTTP-only browser nonce, and includes a hash of the current password verifier version so a password rotation cancels pending enrollment. `userVerification: required` and `residentKey: preferred` support both discoverable and older non-discoverable security keys. Registration never replaces a password, TOTP or recovery mechanism.
- **Discoverable login**: no email is supplied; the browser selects an enrolled credential. Only after validating the authenticator's signature does the server use the stored, globally unique credential ID to determine the USER. The optional `userHandle` must match the same USER ID. The claimed account or role in request JSON is never trusted. Every assertion requires user presence and user verification.
- **Non-discoverable login**: specifying an email requires the current password first, with source/account rate limits. Only this proof authorizes disclosure of that user's `allowCredentials` IDs/transports. WebAuthn then authenticates the credential; this yields a session marked `pwd` + `webauthn`, with **no** synthetic `mfa`.
- **Management**: the security page lists, names, and revokes credentials. Each write requires session-bound CSRF, fresh password and current TOTP if configured. Account and live session locks serialize mutations with logout and account deactivation. A session authenticated by passkey alone cannot enroll/revoke credentials without knowing the password.

The server stores only credential ID, COSE public key, counter, backup eligibility/state, transports, optional display name, timestamps and revocation. It never stores fingerprint/PIN/face data, private keys or raw challenge material. Challenges are stored as SHA-256 digests and are consumed by a single guarded database update, including before failed signature verification. An expired or already-consumed challenge cannot create another session. Bounded cleanup removes expired challenge rows. Signature verification uses `@simplewebauthn/server` and exact origin/RP ID. Authentication uses a counter compare-and-swap and separate revision CAS, including when synced authenticators report counter zero. A zero counter is not evidence of tampering; nor does a nonzero counter prove cloning impossible.

Only verified assertions create an active USER session, and a successful commit includes minimized security audit events. Passkey-only sessions set `authenticationMethods: ["webauthn"]` and OIDC `amr: ["webauthn"]`, `acr: "urn:virki:loa:1"`. Password + passkey records both methods but still never self-promotes to `mfa` or `loa:2`. OIDC freshness, grant checks and project boundaries remain enforced separately.

## Adversaries, limits, recovery

Phishing origins, wrong RP hashes, missing UV, substituted public keys, switched user handles, replay, concurrent assertions, revoked credentials and changed account state must all be rejected. WebAuthn verifies possession of a credential; it cannot guarantee that a synced passkey resides only on physical device hardware or that the sync provider is trusted. A compromised logged-in browser may start a ceremony but cannot enroll or revoke without password (plus configured TOTP). The server does not grant stronger ADMIN assurance based on a passkey.

Loss of all passkeys does not disable password login or existing email/TOTP and recovery procedures. Recovery never discloses or reconstructs private passkey keys; after authenticating through the established recovery flow, a USER can revoke lost credentials and enroll new ones. Disabling the rollout flag is the immediate operational rollback; removing credential tables would irreversibly discard enrolled passkeys and is not a normal rollback.

Before enabling in production, obtain independent security review, locally exercised disposable PostgreSQL adversarial tests, browser virtual-authenticator E2E and manual coverage of platform authenticators and physical security keys. Real cloud devices, sync-provider behavior and accessibility across mobile browsers still require release-specific verification.
