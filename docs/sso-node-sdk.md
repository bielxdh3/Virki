# Node.js confidential RP example: `@virki/oidc-node`

Virki is the OIDC identity provider; an external relying party (RP) owns its application, its own sessions and permissions. `examples/oidc-node-rp` is a minimal **Node.js 22 ESM** RP using Authorization Code with PKCE S256, a confidential client, server-side state/nonce, and an independent PostgreSQL database. It neither receives nor forwards the central Virki session cookie. This sample is for local, disposable validation until the release gates below are satisfied.

## Provision the confidential connection

In Virki Hub, an authorized admin must register the application's **canonical HTTPS origin** and an exact allowlisted callback URI. For this example, set `RP_ORIGIN=https://localhost:8443`, `OIDC_REDIRECT_URI=https://localhost:8443/oidc/callback`; these must match the registration byte-for-byte. The OIDC issuer must be an independently trusted, exact HTTPS origin (normally `https://portal.biel.dev.br`), provided by the operator and **never** taken from an HTTP request, callback or browser input. Store the Hub-generated confidential `client_id` and `client_secret` in server-only environment values; do not check them into Git or send them to the browser. The issuer must authorize that registered connection and an explicit active user-to-project grant. Registration of a connection alone does not grant access.

The library's `createVirkiOidcClient` uses `openid-client@6.8.8`, pins the issuer and metadata endpoint origin, uses `client_secret_basic` authentication against the token endpoint, requires an ES256 signed ID token, checks JWKS signatures, and validates issuer, audience, authorized party, nonce, token lifetime and callback before reporting an identity. Its generated `state` and one-time PKCE verifier are stored exclusively in the encrypted transaction database, with a 10-minute default TTL. The transaction store must atomically **DELETE ... RETURNING** on callback; **SELECT then DELETE is unsafe** under concurrency. JWKS key rotation requires an issuer to publish both valid keys during an overlap and a tested refresh path for previously unknown `kid`. Never replace verification with decode-only token parsing, shared symmetric signing keys, or unpinned alternate issuers.

### JWKS rollover, cache lifetime and removal

The pinned `openid-client@6.8.8` / `oauth4webapi` verifier caches public JWKS for up to **300 seconds** and, for an unknown `kid`, refreshes from the same pinned HTTPS issuer only when the cached set is at least **60 seconds** old. A new signing key first published *after* a client cached the old JWKS may therefore cause fresh callbacks to **fail closed** until a trusted refresh is allowed; the client must never bypass signature verification or fetch a browser-provided JWKS URL. A source-backed regression test exercises the actual public factory with K1 initially advertised alone, K2 published later, rejection during the fresh-cache window, K2 success after a simulated 61-second advance, and K1 rejection after refreshed JWKS excludes it. The clock advance is a **test fixture**, not a claim of 61-second end-to-end issuer availability.

For planned zero-interruption rotation, publish the new *public* key well **before** using its private signing key (at least the observed 300-second maximum cache lifetime, with operational margin), overlap old/new published keys, and retain old verification keys while legitimately issued tokens and cached key sets may still require them. Withdrawing K1 from the issuer JWKS is **not instant revocation** at clients that already cached K1: the test confirms that a previously trusted K1 may still verify until the existing cache expires, then is rejected after a trusted refresh. Emergency key compromise, access-token revocation, existing RP sessions, refresh policies and any faster coordinated invalidation require their own incident-response plan. These 60/300-second values are behavior verified for the **pinned library versions**, not a protocol-wide guarantee or a promise about untested future upgrades.

## Local setup (disposable RP database only)

1. Use Node **22.13+** with npm 10.9.3+. Build the actual SDK distribution: from the repository root run `npm install` and `npm run build --workspace @virki/oidc-node`. The built SDK must export `createVirkiOidcClient`, `randomRpSessionId`, and `EncryptedPostgresTransactionStore` from `@virki/oidc-node/postgres-store` as ESM, with the `dist` folder available. In `examples/oidc-node-rp`, run `npm install --ignore-scripts`; the example's private package depends on `file:../../packages/oidc-node` plus its own `pg` driver. Verify the package's local file dependency actually resolves to the built `dist` before running. These steps require the SDK build to be finalized first.
2. Create a new, disposable PostgreSQL database owned by the **RP**, with a dedicated login role, no issuer production connection or shared credentials. Apply `examples/oidc-node-rp/schema.psql.txt` once using `psql -f examples/oidc-node-rp/schema.psql.txt` and the RP's controlled migration role. The `.psql.txt` extension keeps reference DDL distinct from prohibited database dump/backup artifacts. PostgreSQL column `"expiresAt"` **must** be `TIMESTAMPTZ`; `"stateHash"` is a SHA-256 hex identifier, and `"ciphertext"` holds the AES-256-GCM transaction. `"VirkiRpSession"` separately holds only a **hash** of the RP session cookie, trusted identity reference, expiry and encrypted server-side token. Its hash primary key makes session lookup unique and revocation a single DELETE.
3. Copy `.env.example` into **untracked**, local `examples/oidc-node-rp/.env` and replace *every* placeholder. Generate an independent 32-byte hexadecimal `RP_ENCRYPTION_KEY_HEX` (64 hex characters) with `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`; keep it in an access-controlled secret store outside Git. The flow store derives no key from passwords; the RP session token uses a separate HKDF-derived AES-GCM key and binds its ciphertext to the session hash. Protect and back up the keys under an operator-approved plan; losing a key makes existing flows/sessions undecryptable (safe invalidation).
4. Generate a trusted local TLS certificate for `localhost` with a local developer CA, such as `mkcert -install` then `mkcert -cert-file certs/localhost.pem -key-file certs/localhost-key.pem localhost`. The example opens its **own HTTPS** listener on `127.0.0.1:8443` by default; use `https://localhost:8443` from a browser that trusts this CA. The cert/key files should be untracked, permission-restricted. Use a registered exact HTTPS callback; no HTTP fallback, wildcard redirect, automatic public deployment or `rejectUnauthorized:false` bypass. For non-loopback PostgreSQL, supply `RP_DATABASE_SSL_CA_FILE` with a trusted CA; the sample refuses remote DB connections without it. **No URL query parameters or fragments are accepted in `RP_DATABASE_URL`**, not just `sslmode`: `pg@8.16.3` parses connection-string overrides after its explicit TLS options, and values such as `?ssl=0`, `?ssl=no-verify`, `?sslcert=` and `?sslrootcert=` could otherwise replace the pinned CA or disable certificate validation. Set TLS policy through the dedicated CA file only. The no-network regression test checks these negative URL variants before creating a pool; real remote DB hostname/certificate validation remains an external operational gate.
5. From `examples/oidc-node-rp`, run `npm test` and then `npm start`. Open `/`, click **Sign in through Virki**, complete authentication through the issuer, and verify the callback creates a *new* local RP session. **Sign out locally** performs a same-origin POST that deletes the RP session; `RP_REVOKE_ON_LOGOUT=true` additionally requests token revocation in the back end, when the issuer supports it. It does not terminate Virki's central portal session. A successful sample login never proves authorization to an application feature: the RP must authorize each sensitive operation according to its own rules.

### Database privilege and cleanup boundary

The application role needs parameterized `SELECT`, `INSERT`, `DELETE` on its **own** three RP-owned tables. No issuer schema or central session table access. Grant schema creation/migration rights only to a separate operator identity. Expired state, preauth intents and RP sessions may be cleaned by a trusted, bounded scheduled RP job using the three fixed DELETE queries at the bottom of `schema.psql.txt`; expired records are **also** rejected at use time. In clustered deployments, use one durable shared PostgreSQL store across all RP processes and hosts. Never substitute a per-process Map for authorization transactions or durable sessions. For remote PostgreSQL, verify TLS and hostname validation, restrict network access and bound connection pools. Limit ingress request rate and maximum body/query size at the trusted proxy and enforce a **shared** distributed rate limiter before release; the example's bounded per-process IP limiter is only a local defense.

## Cookie, browser and token boundaries

The browser submits a **POST `/login`** from the RP origin (validated `Origin`, Fetch Metadata when available, and URL-encoded content type). Before redirecting, the RP generates a cryptographic random `__Host-virki-rp-preauth` value, marks it `Secure; HttpOnly; Path=/; SameSite=Lax` with no `Domain`, and hashes it in the SDK's encrypted state record. Because the issuer's top-level GET return needs the cookie, `SameSite=Lax` is intentional. The callback validates the *one-time* stored state, exact callback and this pre-login binding. A callback without the cookie, with another browser's cookie, repeated state, expired state, malformed duplicate params or failed PKCE/nonce/signature is denied. Callback errors expose no token, query, stack or secret.

After the verified token exchange, the RP atomically consumes the pending preauth intent and replaces its prior RP session (if any) inside a single PostgreSQL transaction, clears the preauth cookie and issues a fresh **independent** `__Host-virki-rp-session` cookie with the same restricted attributes and eight-hour maximum age. An existing session **must** be consumed once by `DELETE ... RETURNING`, then its deadline checked against PostgreSQL `clock_timestamp()` **after** the row lock resolves and **before** inserting the successor. Using `NOW()` is unsafe here: it is frozen at transaction start, so a callback waiting on a lock can unknowingly revive an expired predecessor. A stale, expired, already rotated, concurrently logged-out or nonexistent predecessor fails closed. PostgreSQL row locking ensures that two callbacks racing with the same old session cannot both issue successor cookies. Database insert failure or late expiry rolls back the deletion. The RP never reuses the preauth value as a session, trusts a client-supplied `sub`, puts tokens or claims in the cookie, serializes token results to HTML/JSON, or sends a token to browser storage. Sessions are stored as SHA-256 cookie hashes; the server-only access token is separately AES-256-GCM encrypted with session-hash authenticated associated data. HTTPS-only requests must match the configured `Host` and origin. All responses use no-store caching, no-referrer, a restrictive CSP and anti-framing headers. Avoid enabling request-URL logging at proxies because callbacks contain short-lived codes/state.

`POST /logout` enforces the same `Origin`/Fetch Metadata checks and atomically deletes the session row. A request with neither RP session nor preauth cookie returns HTTP 409 with no Set-Cookie: it cannot prove that another callback is not in flight. A pending-intent-only logout can cancel that known intent but also returns 409 (not success), because other tabs may have different active preauth cookies. A request **presenting a stale or already-rotated RP session cookie** that cannot delete its exact DB row receives HTTP 409 with **no Set-Cookie**: a concurrent callback may have minted a newer session and clearing the browser cookie (or reporting a completed logout) would be misleading and can race its response. Refresh/retry sign-out with the current cookie; do not present HTTP 409 as a completed logout. A successful logout clears both RP cookies. If configured, it decrypts and revokes the **server-only** access token after local invalidation. A token endpoint timeout or missing revocation support cannot resurrect the removed RP session. Never use a GET sign-out endpoint or propagate Virki session cookies to this app. For multiple concurrent sign-in tabs, the browser sends its latest preauth cookie on new requests, but an older callback already dispatched with its own cookie may still complete. A successful logout proves revocation of the exact presented RP session only; it does not cancel independent in-flight logins or provide family-wide linearizability.

## Threats, tests and recovery

| Failure or attack | Required behavior |
| --- | --- |
| Login CSRF, forged `Origin`, cross-site POST, method confusion | Reject before beginning an authorization transaction; only same-origin form POST is accepted. |
| Missing/mismatched/duplicate preauth cookie; replayed/duplicate `state` | Deny callback. The SDK atomically consumes a valid state once; wrong-browser redemption attempts can invalidate it but cannot log in. |
| Wrong callback host, HTTP downgrade, wrong `redirect_uri`, altered issuer metadata | Fail closed before establishing a RP session. |
| Bad PKCE, nonce, audience, ID token signature, issuer, `kid`, expiry or account grant | Deny; do not silently bypass token verification. Evaluate grants at issuer authorization and explicitly validate application permissions within RP. |
| Transaction PostgreSQL unavailable, expired or tampered AES-GCM record | Deny callback; never silently fall back to an in-memory store. |
| Session insert, commit, or rotation failure, stale predecessor, or competing callback | Return generic 503 and issue **no** new session cookie; rollback database changes. Only one callback may consume an existing RP session. |
| Expired/revoked RP session or server restart | Expired rows yield no identity; durable sessions and transactions survive a process restart only while their keys and PostgreSQL remain available. |
| Backend token theft via browser/headers/logs | Tokens only exist transiently in the RP backend and encrypted at rest; inspect reverse proxies, metrics, errors and traces for inadvertent leakage. |
| Revocation endpoint failure at logout | RP session is already deleted; remote token may remain valid until expiry. Record an operator-safe audit signal without token details in a real deployment. |
| Logout races with successful old-session callback rotation | Stale cookie cannot delete the newly issued session: return explicit HTTP 409 and no Set-Cookie rather than a false 303 success; user must retry with current session. A deployment requiring linearizable family-wide logout needs a dedicated lineage/revocation design beyond this example. |
| Key compromise / key rollover / rollback of database | Rotate protected secrets and invalidate stored flows/sessions under a controlled operator procedure. Key rotation needs migration or coordinated invalidation; prevent restoring old session rows and old encryption keys together. |

Run focused security tests with `npm test --prefix examples/oidc-node-rp` (PowerShell: `node --test examples/oidc-node-rp/app.test.mjs examples/oidc-node-rp/security.test.mjs examples/oidc-node-rp/server.test.mjs`). The tests verify cookie flags, duplicate-cookie rejection, CSRF/origin, TLS/Host, callback parameter duplication, replay denial through a fake one-time SDK, independent session rotation, local logout/revocation and sensitive data not appearing in HTTP responses. These are **unit/smoke tests with a stubbed SDK and fake PostgreSQL**. They are not evidence of a real OIDC issuer flow, ES256/JWKS rotation or PostgreSQL atomicity across processes. Separately run SDK protocol tests and an isolated PostgreSQL concurrent-consume test, then repeat with TLS and a real registered test connection. Run the repository `npm run secrets:scan`, `npm run lint`, `npm run typecheck`, `npm run prisma:validate`, `npm run build` and `git diff --check` for the integrated commit.

The required extracted package layout is the one described above, and `tsx` must be installed locally for Linux/Node22 or selected via `VIRKI_OIDC_TSX_PATH=/absolute/linux/tsx/dist/cli.mjs`. ### Durable preauth cancellation and concurrent logout

The RP database owns **three** separate tables: encrypted SDK flow state (`VirkiOidcLoginFlow`), a short-lived hashed browser-intent fence (`VirkiRpPreauth`), and hashed independent RP sessions (`VirkiRpSession`). A `POST /login` commits its `VirkiRpPreauth` row before issuing the `__Host-virki-rp-preauth` cookie. A verified callback must atomically **DELETE ... RETURNING** that unexpired intent and insert the new RP session in one PostgreSQL transaction, using the same row-lock boundary as logout. No extra Virki central-session access is introduced.

`POST /logout` atomically consumes the presented pending intent and/or deletes the presented current RP session in one database transaction. If logout commits intent removal first, the matching callback fails closed. **Without a live RP session cookie, even a cancelled known intent returns 409 with no Set-Cookie**: another tab may still carry a different pending intent. If callback commits first and logout cannot consume its intent or old session, logout also returns **409 with no Set-Cookie**, never falsely reports completion. Physical PG18 tests exercise both race orders, row-lock waiting, and the new table. Application role requires `INSERT`, `DELETE` and applicable `SELECT` only on these three RP-owned tables. Clean expired intent rows with the dedicated fixed query in the sample schema. A request with **neither** browser cookie cannot identify a login in another tab or in-flight request; it therefore returns HTTP 409 rather than 303. Only an actual deletion of a presented live RP session is reported as successful logout. This conservative behavior changes the former idempotent cookie-less logout contract, and does not claim global/family-wide logout.

### Recovering an already-revoked RP session cookie

A syntactically valid `__Host-virki-rp-session` cookie can remain in a browser after its RP database row expired, was revoked, or was consumed by a concurrent callback whose HTTP response was delayed. Logout using that cookie returns **409 with no cookie clearing** because it cannot prove revocation of a possibly newer session. Previously every fresh callback then failed **503**, making reauthentication impractical until the cookie expired.

On an **explicit same-origin CSRF-checked POST /login**, the RP now checks its **own authoritative PostgreSQL session table** using the presented cookie hash, **the exactly configured issuer**, and `clock_timestamp()`. If still live for that issuer, the browser cookie is preserved and callback must atomically rotate it. If the row is already absent/expired or belongs to a formerly configured issuer, the RP first persists fresh OIDC state and the preauth intent, then returns a login **303 with a session-cookie deletion and a new preauth cookie**. The browser can finish the new login without reusing the invalid predecessor. If the database check fails, the request is **503 with no Set-Cookie**; never fall back to a local Map or claim successful logout. This is **explicit reauthentication**, not revocation or instant global sign-out.

If an earlier callback commits S1 but its HTTP cookie response is delayed, the browser might start another fresh login while still presenting the consumed S0. The new response safely clears S0 without deleting S1 in PostgreSQL, and both independently verified sign-ins may coexist after reordered responses. Physical adversarial tests prove no consumed predecessor is resurrected; they do **not** claim family-wide session linearizability or that a later response cannot change which valid session cookie the browser retains. Such browser-family epochs/tombstones are outside the issue #59 instant-global-logout scope.

### Issuer migration and stored RP session authority

The example stores the trusted OIDC issuer alongside every RP session. **All authenticated RP session reads, stale-cookie recovery checks, callback predecessor consumption and logout deletion are now issuer-bound**. If an operator replaces configured issuer A with B while retaining an RP database and encryption key containing A's sessions, B must not display A's stored subject as signed in, consume an A predecessor as part of B's rotation, or forward A's encrypted access token to B's revocation endpoint. An A cookie under B is treated as stale: explicit new login clears it; attempted callback rotation is denied 503, and old-cookie logout returns 409 without a false sign-out or sending the token to B. Unit tests and an isolated physical PostgreSQL 18 fixture exercise the boundary without real issuers or bearer secrets.

Changing the confidential **client registration within the same issuer** is a separate operator cutover; the example does not store a per-client session epoch or guarantee ongoing grant authorization at each RP page view. Before rotating client identity/secret or deploying a different application's RP under the same database/key, an operator must revoke/expire prior RP sessions and flow states under a reviewed cutover policy. Implement per-client generation/lineage fencing as a separate design if same-issuer multi-client cutovers must be automatically isolated; do not claim this issuer check proves that property.

### Migrating an existing confidential RP

For an existing server-side OIDC consumer, register its exact canonical HTTPS callback and client with Virki (do not reuse a public SPA secret), create its own isolated PostgreSQL schema and apply the committed three-table sample schema, pin the issuer and ES256 signing policy in server-only configuration, then replace any homemade code/token parsing with `createVirkiOidcClient` and its durable `EncryptedPostgresTransactionStore`. Preserve the existing RP's own application permission checks; map only verified identity claims and create a fresh **RP-local** host-only session after callback. Revoke/expire previous RP sessions and pending authorization states under the prior implementation's operator policy; never migrate raw central Virki session cookies, plaintext tokens or a legacy key into browser storage. Test PKCE, state/nonce, wrong issuer/JWKS, replay, revocation, restart and concurrent callback/logout on a **disposable** database before switching client registration. Perform a controlled cutover/rollback with independent secret storage; do not infer production acceptance from this sample.
## Release / rollback gates

**NO-GO** until the published SDK `dist` contract and imports work under Node 22, its real callback/JWKS/ES256 and rotation tests pass, browser callback cookies work under real HTTPS, PostgreSQL atomic state consumption and restart/multi-worker scenarios pass on a disposable instance, and an independent reviewer verifies session fixation/CSRF, revocation and secret redaction. Confirm issuer-side client registration and grant transitions, shared ingress rate limiting, independent authorization rules, DB TLS/privileges, retention, observability redaction and operator-controlled encryption key storage/rotation. Never interpret this example as a production deployment approval or as proof that issuer grants are checked continuously by the RP.

To roll back the example, stop its local process, unregister/revoke the **test connection** in the intended nonproduction issuer environment after operator review, and expire local RP sessions/flows. Avoid restoring an old RP database and old key after incident-response invalidation, because that can resurrect previously accepted local session records. No central Virki login/session database migration or Cloudflare change is part of this example.
