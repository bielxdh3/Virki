# Issue #90 — DEV V33 same-UID baseline and post-publication admission fencing

The original immutable PR #141 review target `1123f0fde7ca54b6553091f956c4ebd77b91852e`, compared with `main@6802c432163ef7270cdcedc6d9fb55120698a1f3`, was not security acceptance. V32 only tested denied ptrace/procfd access. Host-wide restrictions (Yama, seccomp, hidepid, LSM/container configuration) may cause such denial *without* `PR_SET_DUMPABLE=0`. A denial-only test can return a false green. This V33 incremental patch leaves all V23–V32 blobs, hashes and trees untouched.

## Positive/negative, same-host control design

`TestC1V32SameUIDPeerCannotPtraceReceiver` now spawns two children of **the same test executable, under the same unprivileged UID, parent, proc mount and host runtime**. The unprotected child explicitly verifies `PR_GET_DUMPABLE=1`; the parent MUST first resolve the child's `/proc/<pid>/fd/1`, successfully call `PTRACE_ATTACH`, observe the stopped child and detach cleanly. Only then may a comparable child apply the V32 `PR_SET_DUMPABLE=0` guard after exec, report dumpability zero, and prove `PTRACE_ATTACH` and procfd readlink are denied with access errors.

**Fail closed / INCONCLUSIVE:** if the baseline is root, non-dumpable, ptrace cannot attach, procfd cannot be resolved, or a syscall returns unrelated errors, the mandatory test **fails**, using an explicit INCONCLUSIVE message. The CI must not skip it, silently ignore restrictions, or count an all-denied environment as independent evidence for V32. This test establishes V32's incremental process-boundary effect **only on the tested host** and not exclusive filesystem authority.

## Inode-preserving mutation discovered and mitigated

The DEV receiver's V23 `renameat2(RENAME_NOREPLACE)` has a final stage-name identity check. A hostile same-UID process can overwrite an approved *file in-place after the final pre-rename content scan* without changing its inode or the destination directory inode. The previous postrename check only compared the directory identity, so it could mistakenly return `nil` (admission) while an attacker changed the published bytes. V33 adds another FD-rooted membership and content hash verification **after** the final parent fsync and destination-identity check. Its new fault-seam tests write `EVIL` into the same verified file inode, or inject an unexpected `secret.env` entry after publication; both must return a `V22PublishedButUnadmittedError` and never report successful admission. The fault seam remains private to the tests and the production transfer entrypoints remain unchanged.

**Limits:** both attacks can leave rejected data *temporarily visible* at the destination. A peer with the same UID could also mutate after the last verification. Neither an additional hash nor a pathname lookup eliminates those races. A provably exclusive receiver UID and private mount namespace, or a separately privileged inode-custodial publication broker, must be provided and adversarially verified before C1 is admitted. No real origin, deploy, release or prod file is touched.
