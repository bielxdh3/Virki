## PR #70 P1 follow-up: essential ACR and provider session reuse

- Reviewed starting head: `1590eb259c3ff0a715932d2fcc8a8a5755f69cf7`. Focused code and regression commit: `e74dcdee9674f68d6443d3abba772cac6d216ef9`. This ledger update is committed separately so it can identify the verified code revision without a self-referential commit hash.
- **RED, actual provider and disposable PostgreSQL:** after password-only authentication and prior consent, a new authorization request with mixed voluntary `acr_values` and essential MFA-only `claims.id_token.acr` went directly to the callback with no new interaction. The code exchange returned HTTP 200 and an ID token with `acr=urn:virki:loa:1`; the central session recorded `pwd`, and AMR was not requested in that token. No MFA was established.
- **Change:** the pre-reuse assurance policy reads the provider-validated original `claims` parameter, using the same essential-ACR parser as the interaction handler. Explicit essential alternatives are checked against both the central authentication methods and the provider session ACR. A claim marked essential without `value` or `values` accepts either supported local ACR; malformed or unsupported explicit restrictions fail closed. Voluntary ACR preferences retain truthful fallback.
- **GREEN, final source:** `node node_modules/tsx/dist/cli.mjs --test apps/issuer/src/authorization-policy.test.ts` passed 15/15; `node scripts/integration/run.mjs --local apps/issuer/src/issuer-interaction.integration.test.ts` passed 41/41.
