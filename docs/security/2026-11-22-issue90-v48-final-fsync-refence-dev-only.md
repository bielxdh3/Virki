# Issue #90 — V48 DEV-only: terminal EIO after in-flight fence unlink

An independent read-only adversarial review of the synthetic V40 root ledger reproduced a **recoverable last-fsync error gap**. Once the HMAC log and checkpoint were durably committed, the V40 implementation unlinked `.virki-v40-inflight` and called a final trust-parent `fsync`. If **that final fsync returned EIO**, the first claim correctly returned an error, but the marker was absent; a different properly signed V15 *test* permit could be admitted by a restarted process without manual reconciliation. This did not forge a permit or enable production publication, but was inconsistent with the V40 contract that *any ambiguous durability error* keeps manual recovery mandatory.

V48 adds a distinct injection hook for the **last** trust-parent fsync (not the existing checkpoint-parent hook). After a final-fsync error, the exclusive ledger lock holder attempts to atomically recreate `.virki-v40-inflight`, write `V40_INFLIGHT`, fsync the file and fsync the parent, then returns the original EIO as a terminal manual-recovery error. A focused root-only Go test injects EIO at exactly that point, verifies that the HMAC ledger/checkpoint could be internally consistent, confirms the marker was durably restored, and requires both the original and a **different signed permit** to be refused after independent process restarts. Normal success remains capable of accepting successive different signed epochs. Tests do not bypass checksum, owner-signature or replay assertions.

This is a **best-effort fail-closed response to a recoverable final fsync error**, not a power-loss or hardware-durability theorem. If storage continues returning I/O errors, even re-fencing may fail; the caller returns a terminal error but cannot guarantee future state without independent trusted storage/operator reconciliation. A root adversary who can roll back key, log, anchor and marker together remains outside V40's DEV threat model. No C4 production signing, release authority, autonomous recovery, deployment or persistent host configuration is introduced.
