# Isolated staging email-worker identity — offline role contract

**Status: LOCAL POSTGRESQL ACL PROOF ONLY / STAGING DELIVERY NO-GO.**

The source includes a separate worker-only PostgreSQL role and a Compose
override for a **manually authorized, independently isolated staging host**.
Neither file is part of ordinary stage, deploy, start or restart commands.
Stage keeps the worker OFF. No production database changes, provider delivery
or deployment are authorized by this document. Never use the helper as a
Docker Postgres entrypoint initializer: the mail tables must first exist
from committed Prisma migrations.

## Approval and provisioning gates

An independent owner must identify and approve the **exact** staging host,
DB host/name, immutable image/SHA, dedicated test identities, distinct
runtime/migrator/worker credentials, relay account, permitted recipient
inboxes, sending rate, TLS trust, monitoring, rollback owner and test window.
None may reuse production or deManage assets. If any fact cannot be proved,
the outcome remains **NO-GO**.

After all migrations on the approved isolated staging database, and with
the worker still OFF, a separately authorized operator can inspect the
postmigration script:

- infra/postgres-init/11-virki-email-worker-role.sh

It requires a unique 64-hex worker DB password, distinct from the
bootstrap/runtime/migrator/audit-maintenance secrets. Credentials stay in
the operator-owned secret mechanism; do not commit integration env files,
put passwords in command arguments, or work around a blocked VM operation.
The operator must first derive a fresh SCRAM-SHA-256 verifier on a trusted
local Node runtime using `scripts/staging-email-worker-scram.mjs`, with
`VIRKI_GENERATE_EMAIL_WORKER_SCRAM=operator-approved` and the password
supplied **only through an approved secret environment**. Provide the
resulting verifier as `VIRKI_EMAIL_WORKER_DB_SCRAM_VERIFIER` through the
approved secret channel; the SQL `ALTER ROLE` receives only this verifier,
never the plaintext password. **The verifier itself is still sensitive**:
avoid recording stdout, shell transcripts, pipeline output, PostgreSQL DDL
logs, or deployment diagnostics. Before provisioning, run the SAME local
helper with `VIRKI_VERIFY_EMAIL_WORKER_SCRAM=operator-approved`, the intended
password and verifier in the approved secret environment; it must emit only
`SCRAM_VERIFIER_PAIR=VALID` or refuse. This preflight is not enforced inside
the PostgreSQL shell image: a **separate authenticated SCRAM login** with the
intended password is mandatory before starting the staging worker.
The preflight is deliberately limited to verifiers generated by **this helper**
(SCRAM-SHA-256, 4096 PBKDF2 rounds and 16-byte salt); a verifier produced
elsewhere with different valid PostgreSQL SCRAM parameters is unsupported and
rejected fail-closed. Generate with the documented helper rather than silently
accepting alternate costs or salts.

Provisioning is a single PostgreSQL transaction. It creates/reconciles a
login-only NOINHERIT role without elevated attributes, permits SELECT on
the ciphertext outbox and delivery attempts, narrowly scoped outbox
status/lease updates, and column-scoped attempt INSERT. It cannot enqueue,
change recipients or ciphertext, rewrite attempt receipts, read User,
Session or AuditLog, or create database/schema objects. Excess privileges
inherited from PUBLIC — including TEMP, any other public data relation
and sequences, any PUBLIC table/column grants even on allowed worker fields,
and protected security-schema functions — cause
rejection and rollback of the role reconciliation. The helper clears ambient
libpq PG* connection settings, pins the local PostgreSQL Unix socket on port
5432 and verifies the connected server is not TCP before role mutations.

The worker-only Compose override is:

- infra/docker-compose.staging-email-worker.yml

It requires the separate variable VIRKI_STAGING_EMAIL_WORKER_DATABASE_URL,
without fallback to the Hub DATABASE_URL. The operator must independently
verify the URL authenticates as virki_email_worker, targets the same isolated
staging database used by Hub and has no production endpoint or identity.
This manual override additionally requires the application worker's
`VIRKI_EMAIL_WORKER_SCOPED_ROLE=required` gate. The worker checks the effective
PostgreSQL privilege matrix at startup and before **each** outbox-processing
iteration, stopping further sends when later `PUBLIC` grants widen the role.
The check is not an atomic DDL barrier: a grant racing between a check and
send still requires independent administrator monitoring and a frozen
migration/permission-change window during staging acceptance.
The normal production Compose and role settings deliberately remain
unchanged until independently accepted and approved.

Do not load the override into ordinary production commands or start the
worker until SMTP STARTTLS/AUTH, test recipient allowlist, provider quota,
outbox backlog, worker DB privileges, redacted monitoring and explicit owner
approval have passed. The first permitted send must correlate the outbox
row, attempt row, SMTP acceptance, Brevo provider receipt and a message in
the independently controlled test inbox. An RFC Message-ID or a database
SENT flag is not sufficient proof of receipt. Preserve rollback custody.

## Local evidence versus external acceptance

An additional opt-in local proof at
`scripts/staging-email-worker-full-schema.disposable.mjs` requires
`VIRKI_STAGING_WORKER_FULL_SCHEMA_PROOF=local-disposable-only`. It uses cached,
SHA-verified PG18 and Node22 images on a Docker internal network with **no
published port and no egress**. The database is disposable/tmpfs; the runner
loads all 19 committed Prisma migrations before provisioning `virki_email_worker`,
then runs the actual Prisma Client against that role with a deterministic
in-memory mail transport. It checks positive send/attempt persistence and
negative identity data access, wrong SCRAM password, `PUBLIC` and `MAINTAIN`
drift. It does **not** start the real SMTP worker process or prove Brevo delivery.
For a negative cleanup oracle on a synthetic runner-creation failure, the same
local-only proof accepts `VIRKI_STAGING_WORKER_FULL_SCHEMA_FAIL_AT=before-runner-create`.
It must exit nonzero with the original injected error while still confirming
`LOCAL_FULL_SCHEMA_WORKER_CLEANUP=PASS` for its own database and network;
an inconclusive Docker inspection must instead require owner reconciliation.
Do not enable injection for a successful proof or staging.
The additional diagnostic mode `simulate-runner-ack-loss` models a create
request with **unknown acknowledgement** (without actually creating a runner).
It must fail nonzero with `RECONCILIATION_REQUIRED` and must **not** print
`LOCAL_FULL_SCHEMA_WORKER_CLEANUP=PASS`: even an immediate exact-name
`No such object` cannot exclude a delayed creation after a real request.
The runner still attempts removal of its other known owned resources.

The opt-in script scripts/staging-email-worker-role.disposable.mjs requires
VIRKI_STAGING_WORKER_ROLE_PROOF=local-disposable-only on Windows. It pins
the installed PostgreSQL 18.6 image and local Linux Docker engine and uses
one UUID-labelled container, Docker network:none and tmpfs-only PGDATA.
It tests real SQL grants and denials, transactional refusal before schema
migrations, refusal of unsafe PUBLIC grants, idempotence, and positive
worker-only SELECT/UPDATE/INSERT. It verifies exact container identity
before deletion. No VM, external TCP, SSH, email provider, integration
script or production host is involved.

The minimal fixture and the full-schema/Prisma local fixture are distinct:
the latter proves real scoped worker SQL and persisted outcomes against
19 locally migrated Prisma schemas, but **neither is the independent staging
database or an end-to-end provider delivery receipt**. End-to-end
Hub/PostgreSQL in staging, ADMIN/USER/MFA/WebAuthn on that environment,
worker/Brevo/inbox, rollback and independent operator approval remain
**NO-GO** until directly evidenced. CodeQL and both hosted CI runs were
SUCCESS on the published `e7cff62` commit; later commits must obtain fresh
exact-SHA hosted proof, never inherit that PASS. A GitHub billing failure
before a runner step does not count as CI PASS.
