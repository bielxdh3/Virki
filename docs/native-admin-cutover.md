# Native ADMIN migration: staging, cutover and reversal

This is an operator checklist, **not** permission to deploy or modify production. The target has exactly one authentication system: browser → Cloudflare HTTPS/Tunnel as transport → Virki login and mandatory ADMIN MFA → session/role/elevation/CSRF authorization. The external Cloudflare Access application must not intercept a native login. Cloudflare Tunnel itself does **not** authenticate ADMIN users.

## Selection and invariants

- The production operator environment must **explicitly** set `VIRKI_HUB_PERIMETER_MODE=access` (existing protected deployment or rollback) or `VIRKI_HUB_PERIMETER_MODE=native` (after approval). Missing mode blocks Compose interpolation; any unknown mode fails runtime health, and the Hub never silently treats it as native.
- In `access`, the Hub itself still requires a valid Access JWT. Supply `CLOUDFLARE_ACCESS_AUDIENCE` and `CLOUDFLARE_TEAM_DOMAIN` from the protected operator environment. Missing/invalid values or assertions fail closed, even if the obsolete `CLOUDFLARE_ACCESS_JWT_REQUIRED=false` flag happens to exist.
- In `native`, neither `CLOUDFLARE_ACCESS_JWT_REQUIRED` nor `VIRKI_PRODUCTION_ADMIN_ACCESS_REQUIRED` is needed, and Access audience/team fields may be empty. No second external authentication factor is acceptable. The application's own ADMIN MFA, session, role and sensitive-action elevation remain mandatory.
- Keep PostgreSQL private, application bindings loopback-only on the production Linux host, secret files scoped, trusted Cloudflare client-address provenance validated and throttles fail-closed. No direct publicly reachable origin, emergency bypass account, static edge proof, external VPN or replacement mTLS login.
- Do not set the native mode on the production host merely to make a check green. Production is held at its existing `access` policy until approved cutover, with its original policy/hostname retained as rollback evidence.

## Disposable isolated staging acceptance

1. Confirm a separate disposable database with no production rows or credentials, an explicit staging-only Hub origin, a dedicated Cloudflare Tunnel, and a **separate** staging-only Access application. Record the tunnel, app and DNS identities in a protected off-repository operator inventory; do not commit any token, machine address or personal identifier.
2. Save exact staging Tunnel ingress and Access app/policy configuration for rollback. Confirm neither production Tunnel, production Access policy, production DNS, nor the USER portal is in scope. Verify the app's staged origin is running in `native` mode without an Access JWT and still denies anonymous ADMIN routes; abort if not.
3. Point only the staging Tunnel's ADMIN hostname at the tested staging origin; leave unrelated hostnames and catchall at `http_status:404`. Establish connector health and inspect its actual remote ingress readback. **Only then** move the staging-only Access application to a separate unresolvable parked hostname, preserving its policy/ID, with no matching DNS record; do not remove production Access.
4. From an independent client using real HTTPS and no valid Access cookie/JWT, run `node scripts/native-hub-ingress-preflight.mjs https://<isolated-staging-admin-host>`. It checks `/login` and bare `/recover` return 200 **with their actual Virki login/ADMIN-recovery forms and structurally scoped CSRF fields**, not just a branded error or SSO waiting page. All responses must expose Virki request identity, CSP with frame/base/object restrictions, HSTS (minimum 30 days, allowing the observed Cloudflare edge override of the longer origin policy), `no-store`, anti-framing and `nosniff` headers. All five ADMIN routes (`accounts`, `audit`, `security`, `access`, `connections`) plus `/admin/accounts` with a forged production session cookie must return 307 to their canonical same-origin Virki login. It also repeats `/login` and `/admin/accounts` with a deliberately forged Access JWT, requiring the same native-only behavior. A 302 Access challenge, missing/weak headers, bogus login/recovery HTML, unsafe redirect, 403 on public login, 200 on ADMIN, or 5xx is **NO-GO**. A CSRF token's *shape* here does not prove its signature or functional recovery: require separate DB-backed actions and owner-authorized staging ceremonies.
   The HTML gate requires email, password and scoped CSRF in **one POST login form**, plus a recovery method-selector and a separate rendered React server-action POST form with their own recovery-scoped CSRF fields. Form fragments scattered across a 200 error page, GET-only faux recovery, data-* lookalike attributes, or forms embedded in inert comments/scripts/templates, raw-text tags or quoted HTML attributes must fail. Login and recovery credential/email controls must be enabled, editable and bound to the correct form, not hidden or disabled by a fieldset; a method-selector radio may legitimately be disabled when that recovery choice is unavailable. This structural check does not authenticate the CSRF signature or prove a functional recovery POST.
5. Independently check an anonymous ADMIN audit/security route, a forged session cookie, forged Access assertion, wrong Host/Origin, absent/invalid CSRF and replay attempt. Any unauthorized ADMIN data or mutation is a critical NO-GO. Preserve only redacted status, route and timestamp evidence.
6. With an owner-authorized **disposable** ADMIN and a real authenticator, separately witness password login, fresh MFA, session lifecycle, invalidation, ADMIN-versus-USER authorization, elevation, password recovery and authenticator recovery. Confirm real SMTP STARTTLS/AUTH, receipt, recipient allowlist and rate limits with explicitly authorized provider/test recipients. Browser fixtures, generated TOTP secrets, mocked outboxes, and email-worker unit tests are **not** evidence of a physical authenticator or external mail delivery. Missing credentials/device/provider means **NOT RUN / NO-GO**, not PASS.
7. Demonstrate staging rollback with the **same Access application ID and audience (AUD)**: reattach that exact existing staging app to its original hostname/policy **before** returning the staging Tunnel ingress to 404, observe a genuine Cloudflare Access 302 challenge and 404 fallback, and verify ID, AUD and policy by API readback. Do not delete/recreate the application. Then restore staging Tunnel routing and park the same app again only after native ingress is independently verified. A tested, signed rollback receipt is required before production cutover; do not perform this on production resources during a staging rehearsal.

## First disposable ADMIN on isolated staging (after functional DB/SMTP readiness)

The protected production command `first-admin:prod` is **not** a staging provisioning tool: its database identity/host/port checks must not be weakened or faked. The separate, attended `npm run staging:mfa:bootstrap` entry point uses `scripts/staging-mfa-bootstrap.mjs` and the existing atomic, virgin-database `bootstrapFirstAdmin` transaction **only after** a staging-specific guard passes.

- The operator must independently validate an exclusive non-production PostgreSQL cluster, create separate `virki_migrator` and `virki_runtime` identities with the committed role contract, apply the **official** `prisma:migrate:deploy` command as migrator and verify migration receipts. Do not let the runtime role own the database, create objects or read `_prisma_migrations`. This entry point checks the live database/role/loopback identity, migrator ownership, schema existence, DDL restrictions and migration-ledger confidentiality; an uninitialized database fails closed. The manually scoped staging worker requires `VIRKI_STAGING_EMAIL_RECIPIENT_ALLOWLIST` containing exactly one owner-approved mailbox, identical to the ADMIN bootstrap test inbox; it rejects other recipients before SMTP I/O. This code guard does **not** replace provider-side allowlisting, rate quotas, STARTTLS/AUTH and real inbox delivery proof.
- Only an attended staging operator may set `VIRKI_STAGING_MFA_BOOTSTRAP=enabled`, `VIRKI_STAGING_MFA_TEST_EMAIL` (a single controlled real test inbox) and `VIRKI_STAGING_MFA_CREDENTIAL_DIR` (existing owner-only directory, mode 0700, outside the repository). The Hub must use `NODE_ENV=production`, `VIRKI_HUB_PERIMETER_MODE=native`, canonical **staging-only** Hub/Portal HTTPS origins, separate staging-only signing/encryption/outbox secrets, passkeys off, and a loopback `stage_mfa_YYYYMMDD` database with a distinct runtime login. Do not provide migrator credentials to the bootstrap process. All passwords remain private and absent from argv, Git, logs and comments.
- An operator supplies the explicit terminal confirmation. The CLI generates a random temporary ADMIN password, creates the first account with the application's original transactional virgin-check and audit, and saves the credential in a private one-time file (0600). It never prints the password. A pre-existing credential file blocks a rerun. If the database operation returns an error, **retain the file** until an authorized operator reconciles the account/commit outcome: the transaction may have committed despite a lost response. An incomplete file may be removed only if the failure happened before the database attempt and the file still belongs to that invocation. Its first-login factor is still **EMAIL**, with `emailVerifiedAt=null`, exactly as the regular production code; **do not** run the bootstrap until a separate staging email worker and owner-controlled inbox have actually delivered a test message.
- The owner retrieves the credential file **locally through an approved private operator channel**, completes the email challenge and TOTP enrollment at `/account/security`, stores the resulting recovery codes out of band, signs out and tests the required fresh TOTP login in a real browser. Only the owner may supply the physical authenticator witness. After testing, revoke sessions and securely dispose of the **specific staging account/database**, preserving only redacted receipts. Do not delete or reset any production account, database, Tunnel or Access application.

This CLI does not migrate a database, configure SMTP, change Cloudflare, approve a gate or make an unfinished staging environment usable. Source-level tests and local fixture negatives are not live email/owner-MFA proof.

## Production activation — explicit owner-controlled change

1. Require the owner's separate written authorization for the exact SHA, target production hostname/Tunnel and maintenance window. Verify accepted clean `main`/`origin/main`, exact-SHA **push** CI+CodeQL/SARIF/GHCR digests, remote host identity, `npm run preflight:prod`, backup/restore, migrations, original ADMIN access and an independently witnessed rollback. A green PR check is insufficient.
2. Record and retain the current production Access application **ID, AUD, original hostname, complete policy and policy IDs**, rules, tunnel ingress, operator environment, selected `access` mode, current release and verified backup **outside Git**. Record a read-only API snapshot, independently prove existing login and ADMIN access in `access` mode and pin the existing JWT audience used by the Hub. **Deleting/recreating the Access app is prohibited:** a new application may issue a different AUD and make the saved rollback configuration unusable.
3. Deploy the approved native-capable code through the existing guarded production process **without changing the external Access application**. On the protected production host explicitly select `native`, and verify its local origin serves Virki login directly, denies anonymous ADMIN and enforces internal MFA/session/role/CSRF. If this cannot be demonstrated, stop: external Access stays enabled. The release workflow must not implicitly stop the Tunnel or mail worker outside its approved guarded sequence.
   The guarded production `start`, `restart`, verified maintenance resume/deploy, `start-tunnel` and `health` paths must additionally observe exactly one correctly labeled **running, non-restarting email-worker with no startup crashes**, and verify its own worker-only SMTP configuration before reporting healthy or opening the Tunnel. An unconfigured/restarting worker is a NO-GO even if the Hub and Portal return 200. Private `stage` intentionally excludes and refuses the worker. This is a static-config/process-readiness gate, **not** proof of reachable SMTP, authenticated STARTTLS, provider acceptance, delivery, or approved recipients; those need the separately authorized external witness in step 6 above.
4. **Only after the owner authorizes cutover**, **park the existing production Access app by moving only its hostname to an unresolvable parked staging-independent hostname**, retaining the **same ID, AUD and attached policies**. First prove the target is not serving DNS. Verify all identity fields and absence of the original hostname by Cloudflare API readback; if the platform cannot preserve the same ID/AUD/policies, do **not** proceed. Never DELETE or recreate the app. Confirm the external HTTPS route now reaches Virki login directly, no Cloudflare Access challenge exists, anonymous/forged ADMIN access is refused, and a real owner ADMIN completes MFA. Observe audit, rate-limit, recovery and SMTP acceptance. Never change the USER portal policy.
5. Retain the same Access app and immutable saved configuration during the observation window. On a failure **reattach that same application ID/AUD/policy to the original hostname first**, verify the external Access challenge and API identity/policy readback while Virki native auth still denies unauthorized requests; **then** select `VIRKI_HUB_PERIMETER_MODE=access` with the original saved Audience/Team Domain and restart only through guarded production operations. Confirm public Access challenge, a **positively authenticated owner Access assertion** matching the unchanged AUD, valid Virki owner login and MFA, database invariants and audited recovery. If the app's ID/AUD changed or it cannot be reattached, rollback is **NO-GO**, keep maintenance and escalate; do not silently replace it, bypass authentication or edit identity rows. Validate the guarded restart/rollback path even when hosted CI/GHCR is temporarily unavailable **before** choosing a production window; a locally improvised restart is not an authorized fallback.

## GO / NO-GO boundary

- **CODE GO** means exact-SHA tests, security review and production contracts succeeded; it does not approve public ingress or deployment.
- **STAGING INGRESS GO** requires real TLS/Tunnel with no external Access, public Virki login and recovery, sessionless ADMIN denial and hostile-input negatives. It is narrower than full staging.
- **FULL STAGING GO** additionally requires genuine ADMIN MFA/session/role/elevation, recovery, external SMTP and a witnessed rollback on the *actual* chosen architecture, supported by independently inspectable evidence.
- **PRODUCTION CUTOVER GO** additionally requires explicit owner authorization and guarded exact-SHA production release, restorable backup, independently validated client/transport, live owner verification and recoverable external policy.
- Any missing authority, unavailable hardware, disabled connector, failed/unknown host validation or no authenticated witness remains **NO-GO** for the relevant next stage. Keep PR Draft and production unchanged until its explicit gates are met.
