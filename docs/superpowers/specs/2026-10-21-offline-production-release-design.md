# Virki: owner-approved offline production release (design, not an active gate)

**Status:** proposed on 2026-10-21. No replacement release policy is approved or installed. The current GitHub Actions/CodeQL/SARIF/GHCR release gates must continue to fail closed until a separate explicit owner decision, reviewed implementation and staging verification.

## Goal and scope

Enable a **manual, explicitly selected** Virki production release when GitHub-hosted workflow execution and GHCR publication cannot run. Source control and PR #56 can still use GitHub Git transport; this proposal removes **Actions and GHCR as deployment services**, not the canonical Git origin. Never automatically fall back to offline mode when hosted CI fails. Preserve the complete existing hosted release path.

The only deployment target is the pinned native Debian/Linux Virki host and its protected Virki Compose project. Local Windows, WSL, and Docker Desktop remain development/validation only. The deManage project, credentials, volumes, network, containers and routing are outside scope.

## Explicit security differences

Local CI is not independent hosted CI. Semgrep OSS is not CodeQL `security-extended`, and a manually signed scan report does not create missing CodeQL SARIF evidence. The owner must accept this change in assurance **explicitly** after reviewing scans, test logs and residual risks. No status called `ci=success`, `codeql=success` or "GHCR verified" may be emitted solely because an offline package exists.

## Proposed release gates

1. **Source.** Require a clean `main`, full 40-character SHA equal to the canonical `origin/main`, no Git replace objects, clean staged/tracked/untracked state, and `git archive` of that *exact* revision. Record source remote, source-tree identity, archive byte length and SHA-256. Fail on symlinks, reserved paths, `export-subst`, export-ignore, secrets, unexpected file types and any mismatch. These checks must preserve the existing archive allowlist.
2. **Independent local execution evidence.** Run the full Linux Node 22/npm 10 pipeline and authenticated browser E2E on the **final merge SHA**. Archive raw stage logs and the 19-stage machine-readable result (all 19 exits zero), pinned toolchain versions and zero patch hashes. Run the scoped dependency/secrets/production-boundary tests; build and smoke both production and migrator images for the native host's `linux/amd64` architecture. Run a reproducible pinned Semgrep OSS ruleset, retain raw results, and require a reviewed explicit disposition of each finding. The approval identifies CodeQL as *not run* rather than claiming equivalence.
3. **Artifact identity.** Produce independent, private runtime and migrator OCI image archives via `docker save` (optionally losslessly compressed), recording file sizes and SHA-256 digests. Assert both loaded images have the exact revision/source OCI labels, expected architecture, non-root runtime and production tooling boundary. Do not equate Docker local image IDs with registry manifest digests.
4. **Manifest.** Use a minimal strict canonical v1 schema: full revision and predecessor release revision; pinned expected host identity and `linux/amd64`; archive and both image-archive length/hash; raw CI, static scan, restore-test and smoke-report hashes; scanner rules commit; explicit finding-review decision; creation and expiration timestamps; unpredictable nonce, increasing release sequence and source remote. The schema rejects unknown fields, duplicate keys, oversized data, noncanonical encodings and unsupported algorithms.
5. **Two different signing domains.** A protected builder key signs the manifest after generating evidence. A separate owner-controlled Ed25519 signing key authorizes the **manifest SHA-256 under an owner-specific domain separator** after review. Require distinct pinned public keys and key IDs, bounded validity, a revocation mechanism and no private key in Git, `.env`, the container, CI workspace, bundle or production host. Signing the same bytes must not authorize a different host, predecessor, SHA, image or policy version.
6. **Operator verification before transfer.** The manually invoked offline command checks both signatures and release evidence against the exact clean source; it uses the configured strict SSH host-key pin and eight stable native-Linux identity probes. It verifies remote installation markers, an existing ADMIN, current accepted revision, protected environment files, no active maintenance or unresolved prior attempt, minimum disk capacity for transfer plus expanded images plus backup/restore and a conservative free-space reserve. Failure is terminal, never an implicit fallback.
7. **Host-local trusted verifier.** A separately provisioned root/owner-protected native-Linux verifier (not executed from the untrusted uploaded Git archive) re-verifies the two signatures, immutable evidence and artifact byte hashes, host marker, predecessor, architecture and monotonic anti-replay ledger *before* Docker loads, alias retags, migrations or service changes. Use an exclusive lock and no-follow, owner-only file handling for manifests and ledger. Incomplete/failed attempt stays latched for manual recovery.
8. **Staged release and restoration.** Stage content under unique private Virki paths only; check loaded image IDs, labels and source boundaries. Reuse the hardened existing source inspection, backup-to-durable-file, disposable PostgreSQL restore and committed-migration validation steps before service activation. The maintenance mode must preserve previous image tags/release, database volume, backup and rollback instructions; failure must not silently resume unsafe traffic. Verify health/OIDC, portal ingress, Cloudflare Access on ADMIN only, email prerequisites and deManage continuity. Retain the previous revision and evidence ledger.

## Acceptance and adversarial tests for implementation

Require RED-to-GREEN tests covering wrong SHA/host/predecessor/architecture; stale or replayed approval/sequence; replaced manifest or Docker archive after validation; malformed/colliding/duplicate JSON keys; incorrect signature, key reuse, revoked key and missing key; unreviewed static findings or missing evidence; symlinks/hardlinks/path escape; disk exhaustion; interrupted transfer; two concurrent deployments; unsuccessful backup/restore; unsafe admin/Cloudflare/SMTP state; and rollback after image or migration failure. Verify no deManage resources are targeted. Perform staging rehearsals in isolated Docker fixtures and native-Linux read-only checks; the first live mutation requires explicit owner acceptance of the new assurance policy and exact release digest.

## Required owner-controlled prerequisites

A trusted owner signer separate from the build process; an installed trusted verifier and public-key pins on the Linux host; a new explicitly accepted offline SAST/release assurance policy; actual check of ADMIN presence and restoration safety; free-space budget; and final SHA-specific CI, scan and image reports. Until these exist, **merge preparation may proceed, production release remains blocked**.
