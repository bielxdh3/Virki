# PostgreSQL role separation

## Runtime boundary

Production Compose gives the Hub, issuer, session cleanup, and email worker `DATABASE_URL` for `bielos_runtime`. The one-shot migration service receives only `MIGRATION_DATABASE_URL` for `bielos_migrator`. Audit-log cleanup receives `AUDIT_MAINTENANCE_DATABASE_URL` for `bielos_audit_maintenance`; this credential is attached only to its one-shot maintenance service. PostgreSQL's `POSTGRES_USER` is the bootstrap administrator and is passed only to the database container. The tracked `.env.example` uses separate secrets for the bootstrap, runtime, migrator, and audit-maintenance roles.

The authenticated browser E2E fixture creates a separate, isolated `bielos_runtime_test` identity only in its disposable test container. Its host and database name must still pass the existing explicit E2E database guard. The E2E Hub and issuer use this role only against that disposable database; production Compose does not create or use it.

The runtime role has database `CONNECT`, schema `USAGE`, application table DML, sequence access, and enum/type usage, with no object routine execution, database or schema creation, temporary-table, superuser, role-creation, database-creation, replication, inheritance, or `BYPASSRLS` privileges. The database revokes `CONNECT` from `PUBLIC`; only the bootstrap administrator and explicitly provisioned BielOS roles can connect. Bootstrap, runtime, and migrator passwords must all be distinct. The role script removes existing membership edges involving the runtime or migrator roles and clears excess direct/default object grants to both application roles and `PUBLIC` before applying the intended grants. It grants the migrator `EXECUTE` only on `pgcrypto.digest(text,text)`, required by the committed security-polish migration; it removes `PUBLIC` execution from existing public-schema routines and from the migrator's default privileges. In production and test fixtures, the one-shot migrator is not privileged at cluster level; it owns only the BielOS `public` schema objects. It has database `CREATE` because the committed `0_init` migration starts with `CREATE SCHEMA IF NOT EXISTS "public"`, which PostgreSQL requires at database scope; runtime roles and `PUBLIC` do not have database `CREATE`. That privilege also permits the migrator to create additional schemas, so its credential must remain confined to the one-shot migration service and never be used by application services. The development Compose service alone enables `CREATEDB` on the migrator so Prisma `migrate dev` can create its disposable shadow database. Default privileges grant runtime DML on future migration-created tables, sequence use, and enum/type use.

`pgcrypto` is installed by the bootstrap role. It is referenced by a committed migration but not by application runtime code. The later `CREATE EXTENSION IF NOT EXISTS` migration remains safe for fresh and existing databases because the extension is present before the migrator runs.

## Initialization and legacy volumes

`infra/postgres-init/10-bielos-database-roles.sh` runs automatically only when the official PostgreSQL image initializes an empty data directory. It accepts independent 64-hex runtime, migrator, and audit-maintenance passwords that differ from the bootstrap password, does not print them, restricts all three roles, installs `pgcrypto`, and grants the required access. The audit-maintenance role can connect and use `public`, insert and delete `AuditLog` rows, and select only `AuditLog.createdAt`. It cannot update audit rows or read their message, actor, or metadata columns. Cleanup appends its fixed, sanitized event with a parameterized insert that does not request returned rows, then deletes only expired audit rows. The script also removes old role memberships involving application roles, removes default `PUBLIC CONNECT`, and clears existing direct and default `PUBLIC` object privileges before applying explicit grants. The migration role receives database `CREATE` only because of the committed baseline migration's `CREATE SCHEMA IF NOT EXISTS "public"`; this also lets the migrator create other schemas, so keep its URL limited to the one-shot migration service. It does not receive `CREATEDB`, `CREATEROLE`, `BYPASSRLS`, or cluster privileges. The migration role receives execute access to the one pgcrypto digest overload used by the committed migration; new public-schema routines do not inherit execution by `PUBLIC`. Before changing ownership, it fails closed if it finds public-schema relations or enum/domain/range types outside the current BielOS Prisma schema and migration table, or any non-extension-owned `SECURITY DEFINER` routine in `public`. Review such objects manually; do not broaden the allowlist without evidence.

Existing volumes do not replay initialization scripts. Their owner must inventory the database, restore a verified backup to a disposable PostgreSQL 17 instance, and validate the transition there before applying the same idempotent role script against a persistent database. The script transfers only allowlisted objects in `public`; it does not use `REASSIGN OWNED`, drop roles, remove data, or revoke the bootstrap administrator.

For an existing production volume, do not switch `DATABASE_URL`, `MIGRATION_DATABASE_URL`, `AUDIT_MAINTENANCE_DATABASE_URL`, or `POSTGRES_USER` to the new identities first. During a separately approved maintenance window, retain the cluster's current bootstrap login and add all three application-role passwords to the protected environment. The guarded deployment flow first creates and verifies a backup and validates its restore; only then does it force-recreate the PostgreSQL container while keeping the named data volume, wait for a bounded health probe, and execute the role script from the candidate release through the existing container as the bootstrap administrator. The role script is not replayed by Docker's empty-volume initialization behavior. Inspect role attributes, grants, object ownership, and application health on the disposable restore before applying the same transition to a persistent database. Only after the owner verifies the roles may the protected application, migration, and maintenance URLs be switched. A healthy `pg_isready` result does not prove that a login exists or can authenticate. This repository task has not performed such a live transition.

## Owner-controlled transition

No production connection, role change, migration, backup, or deployment was performed for this change. For a future owner-approved transition:

1. Set independent 64-hex `BIELOS_RUNTIME_DB_PASSWORD`, `BIELOS_MIGRATOR_DB_PASSWORD`, and `BIELOS_AUDIT_MAINTENANCE_DB_PASSWORD` values in the protected operator environment. Set `DATABASE_URL` for `bielos_runtime`, `MIGRATION_DATABASE_URL` for `bielos_migrator`, and `AUDIT_MAINTENANCE_DATABASE_URL` for `bielos_audit_maintenance` using those exact values. Preserve the existing bootstrap role and password until the owner accepts the restore test and rollback plan.
2. Create a protected backup, verify its digest, and restore it into a disposable PostgreSQL 17 instance. Record roles, grants, object owners, routines, extensions, and migration state. Stop if unexpected public-schema objects or non-extension-owned `SECURITY DEFINER` routines are present, or any environment value does not match the reviewed configuration.
3. On the disposable restore, run the role script as the existing bootstrap administrator. It requires the three role-password environment variables and the database name from the container environment. Apply and inspect Prisma migration status through the migration URL.
4. Run Hub, issuer, email-worker, session-cleanup, OIDC, audit, and backup/restore validation with the runtime URL. Verify that runtime DML succeeds, runtime cannot update or delete `AuditLog`, and the maintenance role can append a sanitized cleanup event and delete expired rows while being unable to read audit content or update rows. Also verify that `CREATE`, `ALTER`, and `DROP` on persistent tables, database creation, role creation, temporary tables, and row-security bypass are denied to runtime roles.
5. Keep the bootstrap administrator available for rollback. If runtime checks fail, restore the previous protected service configuration. Do not remove old credentials until a separate owner decision after an independently verified recovery point.
6. Production application requires a separate owner approval and maintenance plan. Apply the reviewed transition through the normal production change process, then verify exact role attributes, grants, migration status, backup/restore, and health. This repository task does not authorize those live actions.

## Disposable evidence

CI runs `npm run test:database:roles` against two pinned, disposable PostgreSQL 17 containers. One initializes from empty storage; the other first applies migrations as the bootstrap role and seeds prior runtime/migrator role memberships plus excess direct and default runtime and `PUBLIC` grants to model an existing transition. Both cases then exercise the migration and audit-maintenance roles, inspect ownership and privilege attributes, prove runtime and E2E-fixture DML, verify column-limited maintenance access and cleanup, assert an unrelated role cannot connect through `PUBLIC`, reject bootstrap password reuse, and assert that runtime DDL is denied. The test removes only the containers it creates. Local execution is unavailable when Docker is unavailable; it must be reported as blocked rather than simulated.
