# Deployment and migration

## Production architecture

Production is operated over SSH on a native Linux host. Windows and WSL are not production targets. The operator must provision the host identity marker, restricted source and backup directories, remote-only environment files, Docker Engine, and Compose before running the preflight. Preflight is read-only: it verifies a pinned SSH destination, eight consistent host probes, the exact marker, file ownership and modes, native Linux, Docker, Compose, and available disk. Missing or inconsistent state stops the operation.

Production Compose keeps PostgreSQL on the private Compose network with the persistent `virki_postgres_data` volume. The public site and Hub bind only to loopback. The Hub serves both the ADMIN surface and the USER portal through `VIRKI_HUB_HOSTNAME` and `VIRKI_PORTAL_HOSTNAME`; the portal surface hostname remains independently configured even when no portal link is provided. `VIRKI_PORTAL_URL` is a runtime server setting used for the public entry point and recovery email URLs. Production Compose leaves it empty when it is not configured, so the portal entry point is not inferred from a hostname setting.

Cloudflare Tunnel routes `biel.dev.br` to the public site and `portal.biel.dev.br` plus `hub.biel.dev.br` to the Hub. Cloudflare Access protects the ADMIN hostname. It must not impose its ADMIN policy on the USER portal. The tracked Tunnel configuration is only a template; production DNS, Tunnel, and Access state must be verified by the operator after a deployment.

## Source and CI gate

The deployment command, commands run through `production-remote.mjs`, and standalone `npm run preflight:prod` require a clean local `main` checkout whose `origin` URL exactly matches the canonical HTTPS remote `https://github.com/bielxdh3/Virki.git` and whose full SHA matches `origin/main`. For that exact SHA, the repository enforces successful completed `push` runs of both the `CI` and `CodeQL` workflows on `main`, retrieves the private GHCR SARIF evidence by its immutable digest recorded in that exact CodeQL run log, and evaluates it with the checked-in reviewed-finding policy. Pull request runs, results for another SHA, pending or failed workflows, missing or tampered GHCR evidence, and unreviewed SARIF violations fail closed. The private GHCR evidence must remain retrievable by the digest bound to that exact successful run; if missing, regenerate evidence by rerunning the approved workflow on the accepted SHA. Never substitute a different revision. GitHub CLI must have package-read access and query the exact Actions workflow runs and their retained logs; the local operator also needs Docker to extract evidence from a never-started OCI container. `npm run preflight:prod` applies this exact-source and static-analysis gate before opening SSH, then checks configured host identity and remote host, filesystem, and protected-file metadata; Docker/Compose availability and daemon access; disk space; `flock`; and reports the count of running container names matching deManage. It does not detect Virki container-name conflicts or check port, Docker-network, or production-root overlap. For deployment, the client uses the successful exact-SHA CI run ID to retrieve the GHCR digest-provenance OCI image by an immutable digest recorded in the CI run log for the native platform. Missing, expired, malformed or cross-run provenance stops deployment. Runtime and migrator images are published to **private GHCR only** after main-push tests and smokes pass; no tarball images are retained as new Actions artifacts.

Private OCI evidence is stored in `ghcr.io/bielxdh3/virki-evidence` under run-scoped tags for CodeQL SARIF and the per-architecture image-digest manifest. Each successful workflow prints the pushed OCI digest in its GitHub run log. Verification obtains only the digest from that exact SHA/run and expected step, refuses duplicate/foreign proofs, pulls `@sha256:` (not a mutable tag), checks OCI source/revision/run/kind/platform labels, copies evidence from a stopped container without executing it and re-evaluates the original SARIF or image manifest. Missing registry access, logs, private-package metadata, digest or content fails closed. This uses GitHub Actions run logs for durable digest anchoring, not quota-limited Actions artifacts. Retain the GHCR evidence images for as long as their run logs are needed for rollback and deployment; no automatic evidence garbage collection is enabled.

## Static-analysis production acceptance

The owner-approved production gate is `OWNER_APPROVED_EXACT_SHA_CODEQL_SARIF_GATE`: (1) exact-SHA PUSH CI succeeds; (2) exact-SHA PUSH CodeQL succeeds; (3) the reviewed SARIF policy succeeds; (4) it reports no unreviewed violation; (5) the private GHCR SARIF evidence from that exact CodeQL run is retained and retrievable by its logged immutable digest; and (6) deployment/preflight uses that same accepted SHA. The production checks enforce this by querying successful `push` runs for `main`, pulling `virki-evidence` from GHCR by the digest logged by the exact CodeQL run, and evaluating the downloaded SARIF with `scripts/codeql-sarif-policy.mjs` before any remote operation. Missing/unavailable evidence must be regenerated for the same SHA; evidence from another SHA or a pull-request run cannot substitute. The reviewed policy remains fail-closed; do not broaden its allowlist to make a gate pass.

GitHub Code Scanning publication is not enabled for this private repository under the current account/repository capability. The owner has explicitly approved the exact-SHA CI, CodeQL, reviewed SARIF policy, and retained-artifact control above as its production static-analysis acceptance gate. Therefore `GITHUB_CODE_SCANNING_PUBLICATION_NOT_REQUIRED_BY_CURRENT_OWNER_POLICY`. This does not mean GitHub Code Scanning is enabled, that alerts are populated, or that the GHCR evidence is a published Code Scanning analysis. Keep CodeQL's `upload: never` behavior and do not claim GitHub Code Scanning alerts exist.

Read-only ingress checks on 2026-10-07 observed HTTPS 200 for `biel.dev.br` and an unauthenticated `hub.biel.dev.br` request redirected to the Cloudflare Access login challenge. Both Cloudflare and Google public DNS-over-HTTPS resolvers returned no A, AAAA, or CNAME records for `portal.biel.dev.br`; direct HTTPS and OIDC discovery requests from this verification environment consequently failed name resolution. This is evidence that those resolvers had no public portal record at check time, not proof of all Tunnel state. Treat the USER portal route and OIDC issuer discovery as `OWNER_VERIFICATION_REQUIRED`; the ADMIN challenge was observed but authenticated Access behavior was not tested. Tracked Tunnel configuration is a template and does not prove live routing. Recheck external ingress before any controlled deployment. These checks are not substituted by the static-analysis gate.

As of 2026-10-07, the GitHub classic branch-protection and repository-ruleset APIs returned HTTP 403 stating that the private repository's plan must be upgraded or the repository made public. Branch/ruleset enforcement could not be verified. Treat this as an `EXTERNAL_LIMITATION`; do not infer required-branch protections from successful CI runs or change repository visibility as a workaround.

Deployment creates a source archive directly from the accepted commit, rejects secret, operator-config, backup, and release-marker paths, and rejects symlinks and other non-regular Git tree entries before calculating its SHA-256. It downloads the accepted CI run's per-architecture GHCR manifest (SHA, run ID, platform, runtime and migrator registry manifest digests), rejects any foreign or malformed evidence and transfers only that verified file and the source archive. The remote checks the transferred SHA-256, authenticates to **private** `ghcr.io/bielxdh3` using a separately provisioned owner-only `read:packages` credential at `/srv/virki/.ghcr-read-token`, pulls runtime and migrator **by digest**, verifies OCI revision/source labels and platform, and retags the validated images locally. The Docker login uses an ephemeral restricted `DOCKER_CONFIG` that is cleaned immediately; secrets are not transferred from Windows or passed into Virki application containers. Production Compose continues to use only those accepted local image tags with `pull_policy: never`, without building or pulling as part of Compose. Node, PostgreSQL, and Cloudflare Tunnel base images are pinned to verified multi-platform image digests. The deployment does not read or upload local `.env`, `.env.oidc`, or `.env.oidc-data`. The remote host keeps these files outside the source tree and links them into immutable `releases/<sha>` directories. Compose uses `.env` for variable interpolation without attaching it to application containers; `.env.oidc` is passed only to the issuer, while `.env.oidc-data` contains the current encryption key and, only during a bounded rotation overlap, the optional previous key; this file is passed only to the Hub and issuer. The Cloudflare Tunnel token is passed only to the Tunnel connector. The remote script also rejects archive links and reserved paths before writing its release marker. It stages the release without changing `current`; after maintenance starts, it creates and validates a fresh backup, applies production migrations, then atomically points `current` at the accepted release. Old releases and backups remain available; routine deployment never clears the production root.

## Fresh installation and private staging

Use `npm run first-install:prod` only for a verified empty Virki production root and a new Virki Docker project. It accepts the exact `main` source, CI images, static-analysis evidence, protected environment files, and host checks. After PostgreSQL is healthy, it explicitly applies the idempotent database-role initializer and proves `virki_migrator` can log in over TCP before running committed Prisma migrations.

Use `npm run first-install:recover:prod` only for the narrowly recognized partial first-install state: no first-install marker, maintenance marker, extra project containers, volume consumers, or network members; exactly the retained accepted predecessor source and the labeled Virki PostgreSQL volume/network must match. A protected checkpoint binds retries to the same accepted SHA and predecessor. The command creates a protected backup outside the repository, restores it to a disposable PostgreSQL 17 instance on an internal network, validates the committed migrations and role contract there, then reconciles the existing database roles, proves TCP login, applies migrations, and writes the first-install marker. It can resume from a fully verified migration checkpoint with no application rows; an unknown or partially migrated schema stops for review. Existing backups and protected environment files are preserved. The recovery path does not delete or recreate the production data volume, start application services, start the Tunnel connector, or change predecessor services.

After that guard succeeds, `npm run stage:prod` starts the Virki application against its separate database on loopback ports `13000` and `13001`; it keeps `cloudflared` stopped and checks image revisions, health, OIDC discovery and unauthenticated Hub denial. This starts the configured email worker as part of the application stack. The operator must account for any queued outbound email when running further staging flows. Staging is not public acceptance and does not prove the live Tunnel destination.

Run `npm run first-admin:prod` from a protected interactive terminal after the first-install marker and new database have been verified. The one-shot bootstrap runs from a restricted Compose profile that receives only the Virki runtime database URL and audit hash secret. It prompts without echo for the owner's email and password, refuses any pre-existing application rows, writes one active but initially email-unverified ADMIN, and records the bootstrap in the audit log. The account must complete the normal email-verification and MFA flow before it can be considered operational. No default credential or public bootstrap endpoint exists.

**One-time October 2026 pre-ADMIN rescue (not a generic deployment bypass):** A verified partial recovery at predecessor `cbd065f2c560fdbc1f32c4c1c4804c352cf84494` encountered the older Prisma advisory-lock bug before any account existed. The otherwise virgin database contains exactly two actorless, successful, zero-change session-cleanup audit rows. A normal upgrade deliberately requires at least one ADMIN, so do not use `deploy:prod` before correcting the first ADMIN. After a new release with the rescue implementation is merged, its exact-SHA push CI/CodeQL/GHCR evidence is green and the owner records a **new** manual approval on the production pointer, run `npm run first-admin:rescue:prepare:prod` from the trusted native-Debian operator checkout with the normal scoped repository/GHCR credentials. It verifies the manual owner approval, exact SHA, retained verified backup, absence of all other application rows, stopped Virki writers/Tunnel, stable predecessor markers and byte-identical Prisma schema/migrations. It verifies the new image by GHCR digest and stages the source under an immutable release directory **without changing current, the deployed revision markers, schema or database**.

Only after preparation succeeds, on a trusted interactive Debian shell execute `bash /srv/virki/releases/<APPROVED_FULL_SHA>/scripts/production-server.sh first-admin-rescue /srv/virki <APPROVED_FULL_SHA>`. Do **not** run this via the restricted loopback SSH key (PTY forwarding is disabled). The script rechecks the same predecessor, previously restore-verified backup and virgin/audit constraints, verifies the staged image's OCI revision/source/architecture, then captures a **new protected pre-ADMIN pg_dump snapshot** (including both audit records) and checks its archive format before requesting credentials. The older clone-restored backup is never deleted or replaced. This new snapshot is format-checked, not yet separately restored; the ordinary subsequent upgrade will run its own full disposable-restore verification. The command uses the restricted bootstrap Compose profile from the new approved image and asks for credentials locally without writing them to shell history. If any constraint changed, it fails closed. After creating exactly one ADMIN, the active release remains the predecessor. Use only the normal protected `npm run deploy:prod` upgrade after confirming public-ingress/Tunnel readiness: that path restores a new backup, checks identity invariants, applies committed migrations and starts routed services. Complete ADMIN email verification, MFA and login validation after the required private ingress is ready; do not enable the unattended deployment agent or perform a public cutover before the owner verifies those gates. A retained restore-verified backup older than 24 hours blocks the bridge; never edit backup timestamps, source markers, or application rows to bypass it.

The normal `npm run deploy:prod` upgrade path is intentionally separate: it requires an existing ADMIN identity, takes and restores a verified backup, and preserves existing identity and recovery invariants. Do not use it to initialize an empty database. Fresh-install success alone does not authorize public cutover; first-admin authentication, SMTP and Cloudflare Access/Tunnel configuration, actual public ingress routing, new-database backup/restore, and rollback must be verified before any legacy service is interrupted.

## Backup and migration order

Before production schema changes, deployment enters maintenance and stops every application writer and the Tunnel connector while leaving PostgreSQL and its named volume running. It then creates a custom-format PostgreSQL backup in the pre-provisioned `backups/` directory, outside all releases. This recovery point is captured only after writers stop, so accepted writes cannot fall between the dump and maintenance. Deployment creates a dedicated transient internal Docker network for a disposable PostgreSQL restore target and the migration runner. Neither joins the live production Compose network; the network has no outbound route or published host port. The clone uses a randomly generated ephemeral password. Deployment restores that same backup, applies every committed migration with `prisma migrate deploy`, runs `prisma migrate status`, and checks that ADMIN/USER counts and each `ACCOUNT_RECOVERY` outbox message's encrypted payload, status, retry metadata, and delivery-attempt records remain unchanged. It then confirms all tagged temporary containers and the network are gone. If cleanup cannot be confirmed, deployment stays in maintenance before production mutation. A missing ADMIN, failed restore, unapplied migration, or changed invariant also stops before production migration. The identity guard requires at least one ADMIN and preserves ADMIN/USER counts across migration; it does not require multiple ADMIN accounts or provide offline sole-ADMIN recovery. See [sole-ADMIN account recovery](admin-account-break-glass.md) for that operational limitation.

Backups are currently retained indefinitely because older dumps do not have durable per-backup restore-verification records and no retention policy has been approved. `npm run backup:inventory -- --directory <absolute-directory>` provides a read-only inventory for an explicitly supplied directory, identifies a backup matching the current verification marker, preserves unknown, partial and symlinked entries, and warns when available filesystem space is below 15%. It has no deletion capability and must be exercised only on disposable fixtures during development; the marker's POSIX owner-only mode cannot be certified on Windows, so an inventory there fails closed for verification evidence. The operator must establish off-site protection, retention periods and an approved deletion process before pruning; never infer that an old or unmarked backup is safe to remove.

After clone validation passes, the same committed migration set is applied to production with `prisma migrate deploy`; migration status and the identity and recovery-outbox invariants are checked again before the application services restart. Final checks verify running image labels, loopback-only bindings, public and Hub health, portal OIDC discovery and PKCE S256, and denial of an unauthenticated request to the Hub ADMIN route. Only after those checks pass does the Tunnel connector start. Any failure after maintenance begins stops routed applications and Tunnel while preserving PostgreSQL and its volume.

Ordinary additive Prisma migrations follow the same order: commit the migration with the matching schema change, allow exact-SHA CI to validate it, restore and apply all committed migrations on the backup clone, then apply those committed migrations on production under maintenance. Existing migration history is retained. Production never uses `prisma db push`, manually rewrites `_prisma_migrations`, removes named volumes, or deletes unrelated Docker resources.

If any step fails after maintenance starts, the script leaves routed application and Tunnel services stopped. It does not silently resume against a partly migrated database. The operator must inspect the preserved backup and migration result, confirm the committed migration status and data invariants, and only then use the guarded maintenance-off action to resume.

## Post-deployment checks

The guarded deployment performs local-origin checks for the public site, Hub, portal OIDC discovery, the Hub ADMIN boundary, and loopback bindings. The operator must separately verify the public `portal.biel.dev.br` route and confirm that `hub.biel.dev.br` remains behind Cloudflare Access. These checks require live DNS, Tunnel, and Access state and cannot be proven by Compose validation alone.

## Private GHCR image and evidence provisioning

Owner-authorized bootstrap has provisioned `virki-runtime`, `virki-migrator` and `virki-evidence` as private packages linked to this repository, using non-deployable placeholders only; real application images and SARIF evidence still depend on successful per-SHA CI workflows. No production host credentials were transferred. Before any production operation, verify all three container packages exist, are **private**, are owned by the expected account and linked to the repository. The CI publication job intentionally **fails before any push** if any required package does not already exist privately and cannot be verified with its scoped `GITHUB_TOKEN`; the owner-authorized first-time bootstrap was completed independently of CI. Provision a minimally scoped, revocable `read:packages` credential **directly on the native Linux Virki host**, outside any Git release, with owner-only mode `0600` and no logs. Confirm that pulling by digest works with that credential in an isolated test. GitHub Actions must use only its short-lived `GITHUB_TOKEN` (`packages: write` restricted to the `main` image job and the CodeQL evidence publishing job); no personal access token is used to publish. The CodeQL exact-SHA PUSH/SARIF policy gate remains mandatory, with private GHCR evidence replacing quota-limited Actions artifact storage. An unavailable SARIF, provenance artifact, registry credential, digest or registry blocks deployment. Do not delete remaining rollback Actions images or private GHCR evidence before a proven alternate recovery path. GHCR pricing and private-package permissions can change: revalidate with GitHub before enabling.
