# Deployment and migration

## Production architecture

Production is operated over SSH on a native Linux host. Windows and WSL are not production targets. The operator must provision the host identity marker, restricted source and backup directories, remote-only environment files, Docker Engine, and Compose before running the preflight. Preflight is read-only: it verifies a pinned SSH destination, eight consistent host probes, the exact marker, file ownership and modes, native Linux, Docker, Compose, and available disk. Missing or inconsistent state stops the operation.

Production Compose keeps PostgreSQL on the private Compose network with the persistent `bielos_postgres_data` volume. The public site and Hub bind only to loopback. The Hub serves both the ADMIN surface and the USER portal through `BIELOS_HUB_HOSTNAME` and `BIELOS_PORTAL_HOSTNAME`; the portal surface hostname remains independently configured even when no portal link is provided. `BIELOS_PORTAL_URL` is a runtime server setting used for the public entry point and recovery email URLs. Production Compose leaves it empty when it is not configured, so the portal entry point is not inferred from a hostname setting.

Cloudflare Tunnel routes `biel.dev.br` to the public site and `portal.biel.dev.br` plus `hub.biel.dev.br` to the Hub. Cloudflare Access protects the ADMIN hostname. It must not impose its ADMIN policy on the USER portal. The tracked Tunnel configuration is only a template; production DNS, Tunnel, and Access state must be verified by the operator after a deployment.

## Source and CI gate

The deployment command and commands run through `production-remote.mjs` require a clean local `main` checkout whose `origin` URL exactly matches the canonical HTTPS remote `https://github.com/bielxdh3/BielOS.git` and whose full SHA matches `origin/main`. Their CI query is pinned to `bielxdh3/BielOS` and must find successful completed `push` runs of both the `CI` and `CodeQL` workflows for that exact SHA on `main`. Pull request runs, runs for a different SHA, pending runs, failures, disabled or missing CodeQL results fail closed. The standalone `npm run preflight:prod` command checks configured host identity and remote host, filesystem, and protected-file metadata; Docker/Compose availability and daemon access; disk space; `flock`; and reports the count of running container names matching deManage. It does not validate the local source SHA or CI, detect BielOS container-name conflicts, or check port, Docker-network, or production-root overlap. The current CodeQL workflow analyzes the revision and stores SARIF as a 14-day Actions artifact without attempting Code Scanning upload; that artifact does not populate GitHub security alerts. For deployment, the client uses the successful CI run ID to download the image artifact for the native Docker platform reported by preflight. Image artifacts expire after 14 days; a missing or expired artifact stops deployment. To recover, rerun CI for the same accepted `main` SHA and confirm its successful result and SHA-labelled image artifacts before retrying the guarded operation. Do not substitute a different revision or publish internal images to another registry. The GitHub CLI must be able to query and download Actions artifacts.

Repository Code Scanning remains a separate owner-managed security-governance acceptance gate. The deployment and `production-remote.mjs` checks verify exact-SHA CI and CodeQL but do not query the Code Scanning API; `npm run preflight:prod` opens SSH and checks host identity, filesystem and protected-file metadata, Docker/Compose, disk, `flock`, and the deManage-name count, but not Code Scanning or host-collision conditions. That implementation limitation does not waive the gate: no production SSH or SCP, including preflight, begins until the owner verifies that Code Scanning acceptance has passed. As of 2026-10-07, `bielxdh3/BielOS` was private, its `security_and_analysis` setting was unset, and the alerts and default-setup APIs returned HTTP 403 stating Code Scanning was not enabled. The repository's Code Security entitlement is not confirmed. GitHub requires an eligible Team or Enterprise plan with Code Security enabled for private-repository Code Scanning ([private-repository guidance](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/private-repository-enablement)). The owner must verify entitlement and policy, enable Code Security for the private repository, and configure or authorize an accepted Code Scanning analysis source for the exact accepted SHA. The current CodeQL workflow deliberately uses `upload: never`; rerunning it or keeping its Actions SARIF artifact does not publish an analysis and does not satisfy this gate. Any accepted analysis path must preserve the reviewed-finding policy enforced by `scripts/codeql-sarif-policy.mjs`: for example, an owner-approved exact-SHA SARIF publication path can use the current workflow's artifact only after that policy passes, without changing `upload: never` or its allowlist. GitHub CodeQL default setup alone does not apply this repository workflow policy and is not sufficient; it can be considered only after an explicit reviewed owner decision replaces that control with an equivalent reviewed-finding policy. Run the accepted source at the exact accepted SHA and verify evidence of a successful Code Scanning analysis in the repository's Code Scanning state/API; API availability or an empty alerts response alone does not prove an analysis ran. Do not make the repository public or treat an Actions SARIF artifact as GitHub alerts.

Read-only ingress checks on 2026-10-07 observed HTTPS 200 for `biel.dev.br` and a Cloudflare Access challenge for unauthenticated `hub.biel.dev.br`. Resolution and HTTPS requests for `portal.biel.dev.br`, including OIDC discovery, failed from the verification environment. Treat the USER portal route, OIDC issuer discovery, and Cloudflare Tunnel routing as `OWNER_VERIFICATION_REQUIRED`; tracked Tunnel configuration is a template and does not prove live DNS, routing, or Access state. Recheck these from the operator environment before any controlled deployment.

As of 2026-10-07, the GitHub classic branch-protection and repository-ruleset APIs returned HTTP 403 stating that the private repository's plan must be upgraded or the repository made public. Branch/ruleset enforcement could not be verified. Treat this as an `EXTERNAL_LIMITATION`; do not infer required-branch protections from successful CI runs or change repository visibility as a workaround.

Deployment creates a source archive directly from the accepted commit, rejects secret, operator-config, backup, and release-marker paths, and rejects symlinks and other non-regular Git tree entries before calculating its SHA-256. It also downloads the exact run's tested runtime and migrator images for `linux/amd64` or `linux/arm64` and calculates their SHA-256 before transfer. The remote verifies both transferred archive hashes, loads the images, checks their revision labels against the accepted SHA, then deletes the image archive. Production Compose uses those exact revision-tagged images with `pull_policy: never`; it does not build or pull application images on the production host. Node, PostgreSQL, and Cloudflare Tunnel base images are pinned to verified multi-platform image digests. The deployment does not read or upload local `.env`, `.env.oidc`, or `.env.oidc-data`. The remote host keeps these files outside the source tree and links them into immutable `releases/<sha>` directories. Compose uses `.env` for variable interpolation without attaching it to application containers; `.env.oidc` is passed only to the issuer, while `.env.oidc-data` contains the current encryption key and, only during a bounded rotation overlap, the optional previous key; this file is passed only to the Hub and issuer. The Cloudflare Tunnel token is passed only to the Tunnel connector. The remote script also rejects archive links and reserved paths before writing its release marker. It stages the release without changing `current`; after maintenance starts, it creates and validates a fresh backup, applies production migrations, then atomically points `current` at the accepted release. Old releases and backups remain available; routine deployment never clears the production root.

## Backup and migration order

Before production schema changes, deployment enters maintenance and stops every application writer and the Tunnel connector while leaving PostgreSQL and its named volume running. It then creates a custom-format PostgreSQL backup in the pre-provisioned `backups/` directory, outside all releases. This recovery point is captured only after writers stop, so accepted writes cannot fall between the dump and maintenance. Deployment creates a dedicated transient internal Docker network for a disposable PostgreSQL restore target and the migration runner. Neither joins the live production Compose network; the network has no outbound route or published host port. The clone uses a randomly generated ephemeral password. Deployment restores that same backup, applies every committed migration with `prisma migrate deploy`, runs `prisma migrate status`, and checks that ADMIN/USER counts and each `ACCOUNT_RECOVERY` outbox message's encrypted payload, status, retry metadata, and delivery-attempt records remain unchanged. It then confirms all tagged temporary containers and the network are gone. If cleanup cannot be confirmed, deployment stays in maintenance before production mutation. A missing ADMIN, failed restore, unapplied migration, or changed invariant also stops before production migration. The identity guard requires at least one ADMIN and preserves ADMIN/USER counts across migration; it does not require multiple ADMIN accounts or provide offline sole-ADMIN recovery. See [sole-ADMIN account recovery](admin-account-break-glass.md) for that operational limitation.

Backups are currently retained indefinitely because older dumps do not have durable per-backup restore-verification records and no retention policy has been approved. `npm run backup:inventory -- --directory <absolute-directory>` provides a read-only inventory for an explicitly supplied directory, identifies a backup matching the current verification marker, preserves unknown, partial and symlinked entries, and warns when available filesystem space is below 15%. It has no deletion capability and must be exercised only on disposable fixtures during development; the marker's POSIX owner-only mode cannot be certified on Windows, so an inventory there fails closed for verification evidence. The operator must establish off-site protection, retention periods and an approved deletion process before pruning; never infer that an old or unmarked backup is safe to remove.

After clone validation passes, the same committed migration set is applied to production with `prisma migrate deploy`; migration status and the identity and recovery-outbox invariants are checked again before the application services restart. Final checks verify running image labels, loopback-only bindings, public and Hub health, portal OIDC discovery and PKCE S256, and denial of an unauthenticated request to the Hub ADMIN route. Only after those checks pass does the Tunnel connector start. Any failure after maintenance begins stops routed applications and Tunnel while preserving PostgreSQL and its volume.

Ordinary additive Prisma migrations follow the same order: commit the migration with the matching schema change, allow exact-SHA CI to validate it, restore and apply all committed migrations on the backup clone, then apply those committed migrations on production under maintenance. Existing migration history is retained. Production never uses `prisma db push`, manually rewrites `_prisma_migrations`, removes named volumes, or deletes unrelated Docker resources.

If any step fails after maintenance starts, the script leaves routed application and Tunnel services stopped. It does not silently resume against a partly migrated database. The operator must inspect the preserved backup and migration result, confirm the committed migration status and data invariants, and only then use the guarded maintenance-off action to resume.

## Post-deployment checks

The guarded deployment performs local-origin checks for the public site, Hub, portal OIDC discovery, the Hub ADMIN boundary, and loopback bindings. The operator must separately verify the public `portal.biel.dev.br` route and confirm that `hub.biel.dev.br` remains behind Cloudflare Access. These checks require live DNS, Tunnel, and Access state and cannot be proven by Compose validation alone.
